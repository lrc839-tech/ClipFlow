# 0.6.2 文件粘贴修复

2026-11-13。

## 修改

文件记录原来同时提供文件引用、UTF-8/UTF-16文件名和Finder图标，0.6.1只移除了图像表示。优先读取文本的接收方仍会选中文件名，形成“粘贴的是名字”的错误回退。

现在普通文件出站只提供每个文件独立的 `public.file-url` 项目，移除文件名文本和其他附带表示。旧 `NSFilenamesPboardType` 数组转换为同样的有序文件URL项目；原始历史字节、指纹和排序保持不变。设置复制、CF菜单点击和全局快捷键共用此规范化逻辑。

这与[Apple建议通过NSURL/NSPasteboard写入文件URL](https://developer.apple.com/documentation/appkit/nspasteboard/pasteboardtype/url)的标准文件表示一致；自动测试对照了原生NSURL写入器的项目类型和文件URL读取结果。

图片仍走原有图像字节路径；不会把图片改成文件名。文件引用损坏、源文件移动或删除时明确失败，不降级发送文件名，也不只粘贴多文件中的可读部分。

## 已验证

- 83项测试、18个套件通过。新增文本优先接收器回归：旧数据能读出文件名，规范化后只能读到文件引用；覆盖UTF-8/UTF-16、原生NSURL对照、多文件/目录顺序、旧文件列表持久化重开和失效引用阻断。现有图片物化、历史缩略图和图片剪贴板读取回归通过。
- 本机真实路径：Finder选中两个文件和一个含子文件的文件夹并复制 → ClipFlow收录 → 设置历史页点击“复制” → Finder目标测试目录Command+V。目标实际产生两个文件和文件夹，含子文件的三份文件内容SHA-256与来源一致，均不是符号链接。
- 在历史页复制后，读取系统剪贴板：三个独立项目均仅含 `public.file-url`，可读出三个文件URL，无文件名文本。
- 更新前备份336条历史及旧App；安装后336条原记录身份与内容指纹全部保留。本次Finder测试另新增测试记录。
- 构建及签名校验通过，本机安装0.6.2。安装包仅本机交付，不上传GitHub Release。

## 待手工验收与限制

- 新版采用临时签名，需要在辅助功能/设备控制和数据访问中移除旧ClipFlow，重新添加实际安装副本，再退出重开。当前没有新版本实键快捷键和CF菜单自动粘贴接收证据；不能由设置页复制的结果代替。
- 授权后：在Finder复制一个测试文件和一组测试文件，到另一空目录，用Command+1或CF历史菜单粘贴，核对数量及内容；再对用户实际目标软件的文件接收区验证。菜单选择后Command+V应继续使用该记录。
- 文件仍保存引用，不保存独立文件副本；移动、删除或失去读取权限会使记录失效。纯文本接收区本身不支持文件附件；尚未宣称钉钉等所有软件均已通过。

下一步是完成本机新签名授权及用户目标软件的实键文件粘贴验收；不在授权验收期间重建已固定二进制。
