# M0：需求审查与验证计划

日期：2026-11-05（Asia/Shanghai）。目标优先级：Option+12 键正确性、连续输入、持久化安全、多格式保真，最后补管理 UI。

## 需求判断和架构边界

项目可使用 Swift + AppKit 独立实现，无需 Hammerspoon。M0 不先实现复杂 UI，采用 Carbon 独占全局热键 + FIFO 任务队列 + CGEvent Unicode 输入实验；同时保留临时剪贴板 + Command+V 对照路径。SwiftUI 管理界面在 M3 再引入。

Carbon 注册针对 ANSI 数字行物理键位：18、19、20、21、23、22、26、28、25、29、27、24，对应 1～9、0、-、=。逐键报告返回码；注册成功并不等于实键捕获成功。独占选项用于暴露已有注册，无法穷尽系统保留键、第三方事件拦截及远程控制环境。见本机 SDK `CarbonEvents.h` 的 `kEventHotKeyExclusive` 和 [Apple 系统版本差异讨论](https://developer.apple.com/forums/thread/763878)。

纯文本直接注入逐 Character 发送，清空事件修饰标志，短间隔串行保留请求。少数目标框架可能忽略 Unicode 附加字符串，按键码重译；不能将一个 NSTextView 的通过外推至 IDE、浏览器或聊天软件。[Apple Unicode 事件文档](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring%28stringlength%3Aunicodestring%3A%29)

剪贴板路径按 `[项目顺序 → 类型标识 → 原始 Data]` 快照，恢复时新建 NSPasteboardItem，不能重用绑定到旧所有者的对象。指纹把项目顺序、排序后的类型名和带长度边界的原始字节纳入 SHA-256；格式不同的同预览内容不会误合并。系统自动生成的 UTF-16 等表示也保留；跨应用语义相等不等于字节指纹相等。[Apple NSPasteboardItem](https://developer.apple.com/documentation/appkit/nspasteboarditem)

系统没有跨应用统一粘贴完成回执。非文本模式的等待只能表示策略窗口，必须在 M1/M2 提供参数与目标应用限制，不能标成“粘贴完成确认”。前台进程变化会取消排队输入；同进程内换窗口、换输入框目前不检测。

恢复前核对 changeCount，遇到后续复制就跳过旧内容恢复，即使新内容字节相同也不覆盖。NSPasteboard 没有公开的跨进程原子 compare-and-swap，检查到写入之间仍有微小竞争窗口；M0 不声称已严格解决任意并发复制。首次临时写入失败后，只在能确认仍拥有本次清空计数时尝试恢复，并报告恢复失败。[Apple changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)

## 权限与数据限制

- Carbon 热键路线不使用广泛键盘监听，不请求输入监控。跨应用发键单独检查 AXIsProcessTrusted 和 CGPreflightPostEventAccess，不能因为注册成功就忽略事件发布权限。
- macOS 15.4 起有独立的 NSPasteboard.accessBehavior。明确拒绝时不把不可读内容当空历史；系统访问提示由用户处理。[Apple pasteboard accessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum)
- 已识别 Concealed / Transient / AutoGenerated / 部分密码类型在请求内容前整体拒绝；无法可靠识别未标记密码，不能承诺全部敏感内容识别。
- 文件只记录 URL 引用。file promises 依赖仍存活的提供者，当前明确拒绝；security-scoped 访问权、私有 UTI 的语义不能靠复制字节续期。普通多 URL 往返与 Finder 实际复制是两项不同验收。[Apple file promises](https://developer.apple.com/documentation/appkit/supporting-drag-and-drop-through-file-promises)
- 默认 64MiB 保留数据上限，整体拒绝超限内容，不裁剪。同步外部提供者可在返回前阻塞或分配内存，当前上限并不是进程内存或读取时长硬限；应在 M1/M2 隔离读取进程后再研究截止与超时。
- 自身写入使用 `.currentHostOnly`，不主动将历史内容广播至其他设备；不能阻止源应用在本工具读取之前已参与的系统通用剪贴板。源代码无网络传输、遥测或云同步。[Apple currentHostOnly](https://developer.apple.com/documentation/appkit/nspasteboard/contentsoptions/currenthostonly)

## M0 明确通过标准

| 实验 | 通过标准 | 失败 / 待验证条件 |
|---|---|---|
| 注册与冲突 | 12 键均返回成功；已有占用时逐键报告可理解原因；解除后可重注册 | 只注册了部分键、无错误，或用注册成功替代按键实测 |
| Option+123 | 独立目标进程严格收到 CBA，焦点不变，无特殊符号；M0 至少一组实键持续按住 Option 建立基线，M1 再做至少 30 组三连与多应用测试 | 缺键、串位、额外符号、焦点变化；自动化按键不进入回调只能记自动化失败 |
| Unicode | ASCII、中文、Emoji、换行在对应目标应用逐字符一致 | 只验证 ASCII，或只观察“事件已发布” |
| FIFO | 快速入队 120 个请求均按顺序完成，最大并发数为 1 | 固定锁丢后续请求、请求内容被后续状态覆盖 |
| 非文本快照 | 至少 PNG/TIFF、RTF/HTML 的实际具名系统剪贴板读取/恢复逐类型字节一致；多 item 顺序一致 | 使用内存 JSON 往返代替系统读取，或将合成 URL 冒充 Finder 验收 |
| 恢复保护 | 无新复制时完整恢复；后续复制（含同字节）保留，新数据不被旧快照覆盖 | 检测到 changeCount 变化仍恢复；一般并发保证仍需实测 |
| 性能 | 分别记录真实端点、样本数、成功率；无样本留空 | 给可见延迟填未经测量的数字 |

## 后续阶段设计（未实现）

M1：后台读取 changeCount、文本历史、原始快照指纹去重、12 键与不可变任务内容、SQLite + 独立 blob、重启恢复。启动先恢复持久化顺序，再把当前系统剪贴板设为监听基线，不自动将启动时内容重复置顶；之后新变化才入库。轮询可能错过两个采样间的中间复制，不能无条件承诺捕获任意频率的复制；变化计数跳跃要可诊断。

存储采用版本化 schema、SQLite WAL/同步策略、先原子落 blob 再提交引用事务。崩溃后启动检查缺失、损坏与孤立 blob，保留并报告待处理项；未知更高版本禁止破坏性迁移。无时间自动清空，无隐式容量淘汰；保存失败不能在 UI 假报已安全落盘。故障注入、崩溃恢复、去重和顺序恢复必须自动测试。系统重启仍由用户实测。

M1 文本门槛对应 T01～T06、T11～T13 的文本相关部分：真实复制 A/B/C、12 键（含空槽）、粘贴排序不变、重复复制置顶、应用重开、权限/冲突、落盘一致性。没有这些通过记录不能进入 M2。

M2：逐格式接入生产历史和粘贴，真实网页→富文本目标、截图→目标、Finder 两文件→另一个测试文件夹（验证源文件还在）、混合队列与慢目标。分别给出保真、降级、等待参数和失败结果。具名剪贴板测试不是 T07～T10 的通过证据。

M3：搜索、删除、暂停、排除应用、存储统计、开机启动与 SwiftUI 管理；兼容性矩阵、打包、公证/正式签名和升级迁移。不会在 M0 自动设置开机启动或清空用户剪贴板历史。
